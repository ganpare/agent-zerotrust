エージェント定義の保存先

A案（OpenCode の設定領域）vs B案（ゲートウェイ管理）— どちらが安全か

やりたいこと： Muse が MCP 経由でエージェントを定義し、そのエージェントにタスクを委譲する。 定義したエージェントは削除できない（残り続ける）。
問題： その定義ファイルをどこに置くか。
A案 OpenCode の設定領域に書く
Muse │ MCP: create_worker_agent() ▼ MCP Gateway │ ファイルを書き込む ▼ ~/.config/opencode/agents/muse-xxx.jsonc ↑ sungo の設定ディレクトリの中 │ ▼ OpenCode │ --agent muse-xxx で読み込む ▼ 実行

長所

  • OpenCode の --agent 機能がそのまま使える
  • 実装が単純（ファイルを書くだけ）
  • 人間が後から手で編集できる

短所

  • Muse が sungo の設定領域に書き込める
  • パストラバーサルで他の設定を壊せる
  • 人間の設定と混ざる（管理が煩雑）
B案 ゲートウェイが管理する
Muse │ MCP: create_worker_agent() ▼ MCP Gateway │ 専用領域に保存 ▼ /mnt/hdd22/agent-zerotrust/agents/ ↑ ゲートウェイ専用（sungo の設定と無関係） │ ▼ dispatch_worker_task() │ プロンプトを instruction に前置き ▼ OpenCode │ 通常の実行 ▼ 実行

長所

  • sungo の設定に一切触れない
  • Muse 専用の領域で完全に分離
  • ゲートウェイが全定義を把握できる

短所

  • OpenCode の --agent が使えない
  • プロンプト注入の実装が必要
  • 人間が手で編集しにくい

詳細比較

観点 A案（OpenCode 設定） B案（ゲートウェイ管理）
sungo の設定への影響 書き込める（危険） 一切触れない
パストラバーサル耐性 脆弱（../../ で突破可能） 固定ディレクトリのみ
OpenCode の --agent 使える 使えない（プロンプト注入）
実装の単純さ 単純 やや複雑
人間による編集 簡単 専用ツールが必要
エージェントの一覧管理 人間の設定と混ざる ゲートウェイが一元管理
バックアップ 設定と一緒 証跡と同じ 22TB HDD

セキュリティ上の決定的な違い

A案の問題： Muse が ~/.config/opencode/ に書き込めるということは、 既存の設定（opencode.jsonc）を壊したり、他のエージェントの定義を改ざんしたりできるということです。 例えば name="../../opencode" のような入力を送れば、メイン設定を上書きできます。
B案の利点： Muse は /mnt/hdd22/agent-zerotrust/agents/ にしか書けません。 ここはゲートウェイ専用の領域で、OpenCode の設定とは完全に分離されています。 さらに、このディレクトリは 22TB の証跡ストアと同じ場所なので、バックアップも一元化できます。

結論：B案を推奨

理由1（安全性）： Muse が sungo の設定領域に触れない。これはゼロトラストの原則 「最小権限」に直結します。

理由2（監査性）： エージェント定義をゲートウェイが一元管理するので、 「誰がいつ何を定義したか」が証跡として残せます。

理由3（実装コスト）： プロンプト注入は instruction の先頭に 定義を付けるだけなので、実装は10行程度です。

B案の実装イメージ：
create_worker_agent(name, description, prompt) → /mnt/hdd22/agent-zerotrust/agents/muse-xxx.json に保存
dispatch_worker_task(agent="muse-xxx", ...) → 定義を読み込み、instruction の前にプロンプトを付けて実行
